# GRY performance report — 2026-11-03

## 1. Environment

| Item | Value |
|---|---|
| Host | Apple M1 Pro, 16 GiB RAM |
| OS | macOS 27.0.1 (build 26A434), arm64 |
| Toolchain | rustc 1.99.1, cargo 1.99.1 (Homebrew) |
| Build | `cargo build --release` (thin LTO, 4 codegen units, stripped debuginfo) |
| SQLite | bundled via `rusqlite`, WAL, `synchronous=NORMAL` |
| Storage | local APFS, ~44 GiB free during the run |
| Network | none at runtime |

## 2. Workload

Deterministic synthetic Go repository generated by `eval/gen_synthetic.py medium --files 10000`:

- 10,002 files, 3,759,198 source bytes;
- 50,207 nodes, 241,735 edges after a full index;
- 4 functions per file, a shared hub and cross-package calls.

This is a different fixture from the historical 10,001-file benchmark in `docs/BENCHMARKS.md`, so
absolute numbers are not directly comparable to the 3.57 s / 233 ms figures. The before/after
comparison below uses the same fixture, binary profile and cache-clearing procedure.

## 3. Method

- Baseline binary: isolated worktree at `01e422f`, built with the same release profile.
- Current binary: working tree after remediation.
- Every full-index sample uses a newly deleted `GRY_CACHE_DIR`.
- Full index: 2 fresh-cache samples per binary.
- Unchanged and one-file edit: 3 samples per binary, after the full index.
- One-file edit appends a comment to the same `pkg0/f0.go` in each run.
- Medians are reported. Peak RSS comes from `/usr/bin/time -l` (`maximum resident set size`).
- No CPU pinning; the machine was otherwise idle but a desktop session was active.

## 4. Results

### Indexing

| Operation | Before p50 | After p50 | Change |
|---|---:|---:|---:|
| Full index, fresh cache | 6,493 ms | 5,963 ms | −8% |
| Unchanged re-index | 349 ms | 229 ms | −34% |
| One-file comment edit | 409 ms | 270 ms | −34% |
| Full-index peak RSS | 1,169 MB | 1,171 MB | unchanged |

Full-index throughput: ~1,540 files/s before, ~1,680 files/s after. The 8% difference is within
run-to-run noise; the incremental improvement is reproducible across the three edit samples
(393/409/442 ms before; 270/330/264 ms after).

### Query latency (current binary, 10k fixture, CLI process time)

| Operation | Observed |
|---|---:|
| `gry search` (BM25, 50 rows) | ~20 ms |
| `gry context` (3200-token budget) | ~10 ms |
| `gry schema` | ~10 ms |
| `gry architecture --aspect overview` | ~10 ms |

These are wall-clock process times including ~9–10 ms process startup, so they are upper bounds for
the in-process handler cost. They were not used to claim a speedup; the remediation did not change
query algorithms.

### MCP discovery

`initialize` plus the three `tools/list` pages (18 tools):

- 3 runs: 20 ms wall time each, including process startup;
- 20,599 bytes of newline-delimited JSON for initialize + 3 pages;
- first page 6 tools, then 6, then 6.

## 5. Bottleneck and correction

The incremental path spent a large share of its time in `Store::prune_orphan_nodes`, called from
`Indexer::index_with_cancel` before the limit check and outside the publication transaction. It
scanned every node to find file paths absent from `file_hashes`. This was redundant:

- delta publication already deletes rows for `deleted_files` and calls `delete_orphan_nodes` inside
  the same transaction;
- full publication replaces the project graph;
- the unchanged fast path has no deleted files by definition.

Removing the call produced the 34% incremental improvement above and removed a pre-publication
mutation that could touch the last valid generation when a run was later rejected for a limit
violation.

## 6. What did not regress

- Full-index time and peak RSS: unchanged within noise.
- Unchanged detection: still 0 parsed files.
- One-file edit: still exactly 1 parsed file.
- Retrieval metrics on `goca-v1`: identical to the baseline binary.
- Graph invariant test after full + incremental + delete: pass.
- The same-size/preserved-mtime edit is now detected; this adds hashing work for every discovered
  file, but the bytes were already read for language disambiguation. The measured incremental and
  full-index results above include that work.

## 7. Database characteristics

- One SQLite file per cache root, WAL mode, 64 MiB page cache.
- Full 10k index: graph plus parse cache, FTS and vectors; peak RSS dominated by parallel extraction
  and the in-memory graph.
- Publication is a single transaction; readers see the previous committed generation until commit.
- `PRAGMA integrity_check` on the local 10k database returned `ok` during the audit.

## 8. Remaining limitations

- 100k files are not measured. The 20k-file result in the previous report remains the measured
  ceiling (1.33 GB peak RSS).
- The full-index before/after difference is within noise; no full-index optimization is claimed.
- Discovery remains I/O-bound: it walks the tree and reads every candidate file (necessary for exact
  hashing and language disambiguation). A metadata cache would trade correctness for speed and was
  not added.
- P99 is not claimed; the sample counts here are 2–3 for indexing and 1 for query timings.
- The machine is a developer laptop, not a controlled benchmarking host.
